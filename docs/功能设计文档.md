# 功能设计文档（初稿 · 内部用）

**系统**：**ThreshCore** — 日志分析、智能诊断、MCP 主机工具与一体化运维控制台。  
**说明**：团队自用初稿，后续会增删合并；**不写固定公文格式**。各功能块尽量统一四个小节：**设计目的** → **为什么要这样设计** → **最终效果** → **解决什么问题 / 边界**。  
**Context Path**：`/award-log`；默认端口 `8088`（可配置）。

## 〇、一条故事线把功能串起来（阅读地图）

设想夜班运维**小张**的一天：

早上交班前先看**仪表盘**里昨天的任务汇总；十点业务报慢，他在**日志分析**页上传 access 与 error 日志，边看**进度条**边和同事说话；报告出来发现某一模板暴增，他点 **AI 全盘诊断**，再对某一行做**单行诊断**；同时他在**工作台对话**里问「这台机磁盘是不是要满」，助手建议他打开 **MCP 工具台**跑磁盘与目录排行，系统弹出**风险分**，他二次确认后拿到结果——晚上科长问「谁干的」，他在**运维链路审计**里用 **traceId** 把整条链路从输入拉到执行摘要，在 **AI 执行审计**里过滤今天的记录。

故事里已经点名：上传分析、任务与历史、报告与图表、导出、AI 诊断、对话、MCP、风险确认、双轨审计。下文把这条线**展开成所有已实现模块**，没有的会标「可选/依赖中间件」。

## 一、ThreshCore 控制台（前端）整体设计

### 1.1 设计目的

用**一个浏览器页面**把「分析日志、看图、对话、调工具、查审计」放在同一心智里，避免运维在五个窗口切 SSH、邮件、聊天软件。

### 1.2 为什么要这样设计

Vue 3 + Element Plus + ECharts 与后端分离，部署上可静态资源挂载也可同源；Tab 分区（工作台对话、工具控制台、执行审计、运维链路审计、日志分析、任务记录、仪表盘、告警历史等）与 README 中菜单一致，减少「能力在后台有、前台找不到」。

### 1.3 最终效果

登录后各 Tab 可走通；带登录态的请求（含部分 SSE）需 `credentials` 与 `/award-log` 前缀一致，否则接口 401。

### 1.4 解决什么问题

把**使用门槛**从「记得住 URL 和 curl」降到「记得住点哪个 Tab」。

## 二、身份与权限（用户 / 角色 / 权限 / 个人中心）

### 2.1 设计目的

区分谁能登录、谁能看日志与 MCP、谁能改告警与用户；个人可改密码与通知偏好。

### 2.2 为什么要这样设计

日志路径与 MCP 若匿名开放，主机侧工具会被脚本滥用。`AuthInterceptor` 保护 `/log`、`/api`、`/admin` 等前缀（以 `WebMvcConfig` 为准）。RBAC 把**误操作**和**恶意扫描**都缩在账号体系里。

### 2.3 最终效果

管理员维护用户、角色、权限点；普通用户只能访问被授权菜单与接口。`UserProfileController` 对应个人中心类需求。

### 2.4 解决什么问题

解决「**谁知道用系统干了什么**」的主体归属，和第八章审计互补。

## 三、日志批量分析（上传 · 异步任务 · 历史 · 取消）

### 3.1 设计目的

支持**单文件 / 多文件**上传，后台**异步**跑完 Drain-Plus 模板归纳、单行时间与协议解析、严重级别、启发式异常与（可选）决策融合，结果落库并生成**可下载**的报表数据。

### 3.2 为什么要这样设计

- **大文件**：分片读 + 并行处理 + **按分片顺序合并**，保证行序与 `sourceLineIndex` 与时间线一致。  
- **多格式**：`LogLineParseSupport` 串联 Linux/syslog/journal 碎片、容器、Nginx/中间件等 `ServerLogParseSupport`，避免大量「时间未知」。  
- **时间诚实**：解析失败用占位，**禁止**用 `new Date()` 冒充日志时间。  
- **任务模型**：`AnalysisTaskManager` 管状态，支持轮询进度、取消、历史分页，避免 HTTP 长连接占满线程。

### 3.3 最终效果

「上传 → 进度 → 报告/图表 → CSV/HTML 下载」；任务可取消；历史可翻页追溯**当时**分析的是哪份文件。

### 3.4 解决什么问题

解决传统「记事本打开 2G 日志」与**说不清异常从哪一行开始**的问题；为告警与根因分析提供**统一事实源**。

## 四、报告 · 仪表盘 · 导出

### 4.1 设计目的

把模板分布、严重级别、Top 模板、时间线等变成**图与表**；导出 **CSV/HTML** 与界面同源路径 `{user.dir}/target/output/{taskId}/`（运行环境为准）。

### 4.2 为什么要这样设计

值班交接需要**可粘贴进周报的表格**；HTML 便于打印归档。导出与内存报表共用同一分析结果，避免「页面上一个数、Excel 里另一个数」。

### 4.3 最终效果

仪表盘聚合多任务视角（与前端页面对齐）；下载接口按 `taskId` + 类型。

### 4.4 解决什么问题

把分析从**看一眼**升级为**能带走、能对比**。

## 五、实时日志分析与日志流（WebSocket）

### 5.1 设计目的

对**持续到达**的日志做与批量**同一套** Drain 与单行解析；可选把解析结果索引进 ES；可选 `/ws/logs` 推送日志流给前端大屏。

### 5.2 为什么要这样设计

实时与离线两套算法会撕扯信任；故复用 `DrainParserFactory` 与解析链。`RealTimeLogAnalyzer` 侧补齐与批量一致的**容器特征**等增强，避免两条管道口径不一。

### 5.3 最终效果

边采集边看时，模板 ID 与严重级别与事后补分析可对齐；未开 ES 时仍解析，仅少检索能力。

### 5.4 解决什么问题

解决「**监控上看见的**」和「**下班导出的报告**」对不上号的经典矛盾。

## 六、AI 全盘诊断 · 单行诊断 · 聊天分析

### 6.1 设计目的

- **全盘/定向诊断**：基于任务结果与抽样片段调用大模型，输出根因与建议。  
- **单行**：用户对某一行点了再诊，上下文更窄、响应更快。  
- **聊天分析**：`ChatAnalysisController` 路径下，就用户问题和选定日志片段做问答式分析。

### 6.2 为什么要这样设计

诊断不是裸调 API：`AiDiagnosisContextBuilder` 做模板多样性、基线样本、按行序、长度上限；提示词里约束**不编造时间/次数、不虚构 TraceId**，减少幻觉污染排障。聊天侧同样有输入长度与证据边界。

### 6.3 最终效果

分析页按钮可触达三种深度；结论应能**指回日志原文**才算用上系统。

### 6.4 解决什么问题

解决「**只有统计没有解读**」或「**解读张嘴就来**」两种极端。

## 七、统一助手与自然语言工作台（SSE）

### 7.1 设计目的

`/api/assistant` 流式对话，把**口语诉求**转成：建议、工具调用意图、或引导上传日志。系统提示里**对齐本机 MCP 工具英文名**，减少模型发明不存在的工具。

### 7.2 为什么要这样设计

模型只做语言层；**真正调 OS** 必须落到 MCP + 安全门。流式输出适合长回复阅读。

### 7.3 最终效果

工作台 Tab 里可完成「问—答—（需要时）转工具台执行」的闭环；前端 `OpsChatInterface` 等可与 MCP 元数据合并展示。

### 7.4 解决什么问题

让不熟悉命令的同事也能**用同一套受限能力**排障，而不是私下要 root 密码。

## 八、MCP 工具链（注册表 · HTTP 执行 · 与 Disk 排行的关系）

### 8.1 设计目的

把主机侧能力做成**可列举、可传参、可测**的 Bean；`McpToolRegistry` 注册包括但不限于：`LogAnalysisTool`、`DiskTool`、`DiskAnalyzeTool`、`ProcessTool`、`SystemLoadTool`、`NetworkTool`、`OsInsightTool`、`ConfigCheckTool`、`PrivilegeTool`、`CleanTempTool`、`LogCleanupTool`、`ServiceRestartTool`、`FirstMcpTools` 等。磁盘目录热点排行由 Disk 相关能力提供（README 写 DiskInsight 由 `rankDiskUsageUnderPath` 等入口衔接）。

### 8.2 为什么要这样设计

**一处注册、统一出口**：`McpExecuteController` 拉列表、执行、确认执行；加工具主要加 Bean + 注册 + 单测，不把控制器写成圣诞树。

### 8.3 最终效果

工具控制台动态列表；每个工具参数可在 UI 填 JSON 或表单（以前端为准）。

### 8.4 解决什么问题

解决脚本散落、版本不可追、**谁在机器上跑了啥**说不清的问题（与审计联动）。

## 九、安全护栏（统一门 · 注入 · 意图 · 高危命令 · 风险分 · 路径策略）

### 9.1 设计目的

`McpInvocationSecurityGate`：**工具名白名单**、参数条数与单字段长度、指令串总长、与 `PromptInjectionGuard`、`IntentRiskFilter`、`HighRiskCommandDetector`、`AgenticRiskScoreEngine` 联动。`McpSecurityProfile` 区分首次请求 / 已二次确认 / 延时任务，避免同一操作被重复拦死。

### 9.2 为什么要这样设计

概率模型不能当 shell；确定性策略放 Java。`agent.paths.*`（`OpsPathPolicy`）管读前缀、清理根、日志清理根、禁止子串、Windows/Linux 分列；`agent.security.risk-score-*` 划分自动 / 确认 / 拒绝区间。

### 9.3 最终效果

写类工具：`CleanTempTool`、`LogCleanupTool` 等 **默认 dry-run**，真实删除需 **dryRun=false 且 confirmDelete=true**；`ServiceRestartTool` 仅在 `agent.service-restart.allowlist` 内。`MinPrivilegeExecutor` 在非 Windows 开发环境下尽量用 `agent.run-as-user` 跑命令。

### 9.4 解决什么问题

解决误删、注入诱导、参数炸弹；**不是**完整虚拟机沙箱，而是**工程上可运维**的一组底线。

## 十、审计双轨：AI 执行审计 · 运维链路 trace（CoT）

### 10.1 设计目的

- **AI 执行审计**：`/admin/audit/ai` 一类接口列出模型/MCP 相关执行记录（是否放宽只读见 `app.security.ai-audit-relaxed-read`）。  
- **运维链路**：`OpsTraceController`，列表 + `traceId` 详情，**steps_json** 解析为思维链步骤（接收—感知—推理—校验—执行摘要）。  
- **Chat 路径**：生成 traceId，`TraceService` 落库。

### 10.2 为什么要这样设计

出故障要对齐「用户说了什么、系统判了什么、执行了什么」；纯应用日志难检索，结构化审计表可下钻。

### 10.3 最终效果

任何一条敏感链路可凭 traceId **从头到尾**复述，方便内部复盘和对外说明（权限收敛后）。

### 10.4 解决什么问题

解决「**黑盒智能运维**」在事故里无法自证的问题。

## 十一、对话入口安全与聊天侧（ChatController 等）

### 11.1 设计目的

`/api/chat` 等入口在走工具前做注入、高危意图、风险拦截；与 MCP 门互补，覆盖「纯自然语言直驱」的路径。

### 11.2 为什么要这样设计

攻击面不止 MCP JSON，还有**假装闲聊的注入**；需在会话入口就降级或拒绝。

### 11.3 最终效果

拦截时返回可读原因并带 traceId，便于和第十条对照查询。

### 11.4 解决什么问题

补上「**没点工具只在聊天**」也能作恶的空隙。

## 十二、决策管线（规则 · 随机森林 ONNX · LLM · 融合）

### 12.1 设计目的

`IntelligentRouter` / `EnsembleService`：`RuleEngineV2` + `RandomForestDecisionEngine` + `LlmDecisionEngine` 多路输出再融合；`RandomForestDecisionEngine` 读 `log.pipeline.decision.rf.model-path`，缺失则**启发式降级**。`CollaborativeDecisionService` 等参与更复杂协作场景。

### 12.2 为什么要这样设计

单一路径要么死板要么飘；演示机或客户环境未必有 ONNX；故融合 + 降级是**交付**策略，不是论文指标。

### 12.3 最终效果

有模型：打分可利用统计特征；无模型：规则 + 启发式仍能跑通告警与分析pipeline。

### 12.4 解决什么问题

解决「**智能化与可启动**」不可兼得时的工程取舍。

## 十三、决策反馈与离线再学习

### 13.1 设计目的

`DecisionFeedbackController` + `ContinuousLearningService`（概念）与 `scripts/ml/train_model.py` 等：导出标注样本，离线训练新 ONNX，再替换 `resources/models/`。

### 13.2 为什么要这样设计

线上服务不应强依赖本机 Python；训练与推理**解耦**，避免部署事故。

### 13.3 最终效果

有标注数据时可迭代 RF；无则跳过，主线功能不受影响。

### 13.4 解决什么问题

让「模型越用越准」有**出口**，但不绑架首次安装。

## 十四、告警全链路（配置 · 历史 · 统计 · 生命周期 · 兼容接口）

### 14.1 设计目的

- **AlarmConfigController**：告警策略读写。  
- **AlarmHistoryController**：历史与统计视图数据。  
- **AlarmLifecycleController**：生命周期（确认、静默等，以接口为准）。  
- **AlarmRuleCompatController**：与旧前端路径对齐的内存规则（重启清空，README 已说明）。

### 14.2 为什么要这样设计

分析结果必须**触达值班动作**；聚合窗口、最小严重级别、推送间隔（见 `alarm.*` 配置）减轻同一故障刷屏。

### 14.3 最终效果

邮件 / 企业微信等 channel 接好即可**对外喊人**；历史可回看某次故障关联了哪批任务。

### 14.4 解决什么问题

解决「**报告看完了没人动**」的断层。

## 十六、日志采集与管线状态（目录 · 可选 Kafka）

### 16.1 设计目的

- **FileLogCollector** 等：按 `log.collector.file` 配置**监听/扫描**允许扩展名与排除目录。  
- **NetworkLogCollector**：网络监听（按需启用）。  
- **Kafka**：`award.middleware.kafka=true` 时启用生产/消费，与 `log.pipeline.kafka` 主题等配置配套。

### 16.2 为什么要这样设计

现场不止「用户手动上传」，还有**持续落盘**与**管线导入**；开关避免开发机没 Kafka 就红字刷屏。

### 16.3 最终效果

`CollectorStatusController` 可看采集健康；Kafka 场景下可走「入 topic → 消费 → 分析」故事。

### 16.4 解决什么问题

把系统从**一次性分析工具**拉成**可持续接入**的平台（在环境具备时）。

## 十七、Elasticsearch · 检索 API

### 17.1 设计目的

`spring.elasticsearch` 开关为 true 且集群可用时，实时/检索类能力索引日志文档；`ElasticsearchController` 提供索引与搜索类操作（以实际方法为准）。

### 17.2 为什么要这样设计

纯 MySQL 扛不住全文与海量检索；ES 作为**可选增强**，关开关即不强依赖。

### 17.3 最终效果

大索引场景下查询体验提升；关 ES 时仍可用上传分析主线。

### 17.4 解决什么问题

解决「**只会 grep 文件**」在集群日志下的乏力。

## 十八、延时运维任务（OpsSchedule）

### 18.1 设计目的

`/api/ops-schedule`：低风险巡检类工具可预约；**高风险写操作默认不进**默认定时列表（以 `OpsDeferredTaskService` 实现为准），避免无人值守删库。

### 18.2 为什么要这样设计

自动化与作死只差一线；延时任务必须比「即时点按钮」**更保守**的信任模型。

### 18.3 最终效果

科长可设「每周一只读巡检磁盘」，而不会误设「半夜 rm」。

### 18.4 解决什么问题

解决「**想定时巡检**」又不想把定时器变成后门。

## 十九、Runbook 审批流

### 19.1 设计目的

`RunbookApprovalController`：`/api/runbook` 提交—审批—执行类流程，把**半标准化处置**纳入系统，而不是口头传话。

### 19.2 为什么要这样设计

高危操作即使技术上允许，也需要**人或角色审批**才符合变更制度。

### 19.3 最终效果

常见故障剧本可固化成可审批的 Runbook（实现深度以代码为准）。

### 19.4 解决什么问题

解决「**口口声声标准化、实际全靠老师傅**」。

## 二十、性能分析（REST + WebSocket）

### 20.1 设计目的

`PerformanceAnalysisController` 提供趋势、基线、多维分析数据；`/ws/performance` 推送性能流，供大屏或详情页刷新。

### 20.2 为什么要这样设计

日志慢往往要**和资源曲线对看**；WebSocket 减轻轮询压力。

### 20.3 最终效果

小张在业务说卡顿时，一边看日志模板爆发一边看 CPU/内存曲线（数据源以采集实现为准）。

### 20.4 解决什么问题

解决「**只看到错误字面值，看不到机器在喘**」。

## 二十一、日志清洗规则（LogClean）

### 21.1 设计目的

`LogCleanController`：维护清洗规则、单条试清洗，让同一类噪声（时间戳、指纹）在进 Drain 前被规范掉，**模板更稳**。

### 21.2 为什么要这样设计

原始日志常带随机 sessionId，会把 Drain 树撑爆；清洗规则相当于**可配置的归一化层**。

### 21.3 最终效果

同型故障能聚到**更少模板**，告警噪声下降。

### 21.4 解决什么问题

解决「**模板爆炸、统计没法看**」。

## 二十二、平台就绪检查（PlatformReadiness）

### 22.1 设计目的

`PlatformReadinessController` 一键或分项检查：DB、可选中间件、关键目录、模型文件等是否**就绪**，上线前自检用。

### 22.2 为什么要这样设计

部署文档再长也不如**自动探针**；适合发布 checklist。

### 22.3 最终效果

运维打开页面或调接口就知道「绿灯能不能演示全套」。

### 22.4 解决什么问题

解决「**谁也没料到这个环境没配 ES**」的临场尴尬。

## 二十三、知识库 · 模板管理 · 规则管理（REST v1）

### 23.1 设计目的

- **KnowledgeController** `/api/v1/knowledge`：运维知识条目，可接 Qdrant 向量检索（`qdrant.*` 配置）。  
- **TemplateManagementController**：日志模板库维护。  
- **RuleManagementController**：业务/告警规则维护。

### 23.2 为什么要这样设计

分析结果要沉淀为**可检索资产**，而不是一次性 HTML；规则与 Drain 模板分离：**前者偏策略，后者偏统计形状**。

### 23.3 最终效果

新人可搜「上次 MySQL 死锁咋看的」；老规则可版本化管理（以表结构为准）。

### 23.4 解决什么问题

解决「**经验只在老员工脑子里**」。

## 二十四、模型评估 · 健康 · 实验与决策 v1 API

### 24.1 设计目的

- **ExperimentController** `/api/v1/experiment`：管线实验。

### 24.3 最终效果

算法同学可迭代 ONNX 与特征，而不改上传分析主接口。

### 24.4 解决什么问题

解决「**一改模型全站抖**」。
