# 2026 操作系统设计赛多智能体赛题适配

## 项目定位

将 ThreshCore 的受控运维处置能力用于 Linux 主机突发磁盘压力与服务异常的联合诊断和恢复。系统从同一组主机证据出发，由多个专业智能体并发分析，再合并为有依赖约束的处置计划；所有写操作继续经过预览、人工批准、统一执行管线、效果验证和审计。

该场景适合本项目已有的日志分析、主机观测、Skill、受控工具和恢复机制。它也能自然拆成并行诊断任务，并通过角色交接发现冲突，例如日志清理建议与服务恢复验证之间的依赖。

## 对赛题要求的场景映射

演示任务：Linux 主机磁盘使用率突然升高，同时一个业务服务出现错误。团队需要判断空间增长来源、评估日志与临时文件清理风险、检查服务状态和配置变更，再生成可批准、可验证、可恢复的处置方案。

| 智能体 | 并行子任务 | 主要输入 | 产出 |
|---|---|---|---|
| 磁盘与主机观测智能体 | 分析挂载点、容量趋势、目录占用 | 磁盘与主机只读观测 | 空间风险摘要、候选目录 |
| 日志诊断智能体 | 分析错误日志与增长来源 | 日志样本、采集时间范围 | 错误模式、日志清理候选 |
| 服务健康智能体 | 判断服务状态及异常时间关联 | 服务状态、健康检查结果 | 服务影响摘要、恢复验证条件 |
| 配置与安全审查智能体 | 检查候选动作是否触及保护路径、策略或敏感对象 | 配置摘要、工具白名单、候选计划 | 风险意见、禁止项和补充条件 |
| 协调与验证智能体 | 汇总各方结论、处理分歧、形成依赖图并验证结果 | 四份并行报告、执行回执、执行后观测 | 最终计划、验证结论和审计摘要 |

前四个角色分别执行可并行的分析；协调角色只在分析报告齐备后运行。执行阶段的前置关系由计划 DAG 表达，例如“确认日志文件归属 → 预览清理对象 → 人工批准 → 清理 → 重新采样磁盘 → 验证服务健康”。任何前置节点失败时，后续依赖节点不得启动。

至少三组双向交互应形成可回放的结构化消息，而非仅在提示词中声称协作：

1. 磁盘观测 ↔ 日志诊断：核对空间增长目录是否与日志增长证据一致。
2. 日志诊断 ↔ 服务健康：交换错误时间窗口和服务异常时间，确认关联强度及其局限。
3. 服务健康 ↔ 配置安全审查：确认恢复动作的影响范围、保护约束和验证条件。

每次消息记录发送方、接收方、任务 ID、证据引用、内容摘要、时间、轮次和关联的任务节点。接收方可提出补证请求，发送方应返回证据或明确拒绝；协调智能体保存最终采纳或驳回理由。不得把模型私有思维过程作为交互记录。

## 当前代码与赛题差距

当前仓库已存在 `AgentTeamService`、团队运行持久化、团队事件时间线、独立的诊断/计划/验证模型调用、人工审批、受控工具网关、执行后验证、前端协作任务页和 `AgentTeams运行与接管.md`。这构成受控执行底座。

现有团队运行文档说明目前是三个模型角色（诊断、计划、验证），执行主流程为顺序阶段；它不能证明赛题要求的至少四种可协作智能体、四个并行子任务、三组双向交互或 DAG 依赖调度已经实现。当前代码搜索也未发现 AIOS-Agent SDK 接入；因此现阶段不能称为已在 AIOS 框架内完成集成。README 中“单机版本”是项目当前定位，不等于 Linux + AIOS + 端侧 7B/8B 的目标环境验收。

| 评分项 | 当前证据 | 尚需完成的实现或证据 |
|---|---|---|
| 复杂任务及不少于 4 个可并行子任务 | 受控运维能力和团队运行已存在 | 固定 Linux 故障场景；实现并行子任务分配和汇聚 |
| 不少于 4 种智能体 | 现有三个角色调用：诊断、计划、验证 | 加入至少四个明确职责的专业智能体，并记录每个角色的实际调用 |
| 至少 3 对不同类型智能体双向交互 | 有阶段交接，未见可回放的双向消息协议 | 实现三对以上请求/答复或质疑/回应，持久化消息与证据引用 |
| 子任务依赖和顺序约束 | 现有主流程有固定阶段顺序 | 扩展为显式任务 DAG，检查环、阻断失败依赖并记录调度事件 |
| AIOS-Agent SDK 与目标环境 | 当前实现基于本项目 Spring AI/Java 编排；新增最小可行性样例，尚未在 AIOS 环境运行 | 先确认 SDK/Kernel 的真实调用与调度边界；再在 Linux + AIOS + 端侧 7B/8B 实机验证 |
| 并发性能提升不少于 20% | 目前没有本场景的串行/并发对照数据 | 固定同一输入、模型、硬件和超时策略，重复测量并保存原始记录 |
| 正确完成复杂任务 | 有工具强验证、批准、恢复和审计机制 | 定义合成故障集与预期结果，统计成功率、误操作和恢复结果 |

## 架构边界与实施顺序

先验证平台，再扩展协作逻辑，避免把赛题要求的调度核心先写到 Java 外围。

1. 运行 [`AIOS + Cerebrum 最小样例`](../../experiments/aios-cerebrum-mvp/README.md)：验证两个角色经 Cerebrum 调用 AIOS Kernel、首轮并发、一次双向消息和合成工具结果；同时检查 Kernel 侧是否有对应调度/上下文记录。这个样例只证明 SDK/Kernel 调用边界，不能单独证明业务 DAG 已由 AIOS Kernel 调度。
2. 根据实跑结果确定唯一的协作运行时。若 Cerebrum/AIOS 暴露的 Agent 运行接口能承接子任务派发、并发和依赖阻断，正式协作图放在 AIOS 一侧；Python 客户端只提交目标、接收状态和展示审计。若 SDK 仅管理模型调用而未管理 Agent 任务调度，先验证可用的 Kernel 原生接口或向赛题维护方确认边界，不在 Java 中先实现平行调度后再浅接 Kernel。
3. 固定可重复的合成故障场景、四类并行子任务、工具范围和正确结果判据；用只读数据跑通报告汇聚与失败阻断。
4. 实现结构化双向消息协议和事件记录，再增加有向无环任务图；依赖校验与失败阻断由最终确定的 AIOS 侧调度层执行。
5. 通过受限 REST 边界连接 ThreshCore。ThreshCore 保留现有预览、人工批准、`OpsExecutionPipeline`、效果验证、恢复和审计，不在 Java 侧复制 AIOS 的 Agent 调度器；Agent 不得绕过服务端安全门直接写主机。
6. 在 Linux + AIOS + 端侧 7B/8B 环境记录 SDK/Kernel/模型版本、量化、硬件、调度事件和运行日志。随后在同一环境比较串行与并发方案，报告中位数、P90、成功率、超时和失败原因。
7. 准备现场演示：提交任务 → 展示四路并发和 Kernel 调度证据 → 查看三组双向交互 → 展示依赖图与失败阻断 → 人工审阅预览并批准 → 验证恢复结果 → 展示审计和对照数据。

## 性能与正确性验收口径

对每个固定测试样本分别运行串行基线和并发方案，保持输入、提示模板、模型与量化版本、硬件、采样策略、超时、工具执行模式一致。预热后每组至少重复 10 次，报告中位数、P90、成功数和超时数，并保留每次运行的开始/结束时间、任务事件和结果摘要。

提速率按 `1 - 并发方案中位耗时 / 串行基线中位耗时` 计算。只有结果达到 20% 且正确率未下降，才可声称满足该评分项。并发运行中模型服务器排队、上下文长度和冷启动也会影响结果，需保留这些条件，不能把任务线程数直接当成性能提升。

正确性至少检查：关键根因判断是否落入标注范围；未授权写入为零；计划依赖顺序正确；工具回执与独立后置证据一致；失败或证据不足时能停止并转人工；需要恢复时恢复结果可核对。模拟工具和测试替身只能证明编排逻辑，不能替代目标主机、AIOS 和真实模型验收。

## 当前结论

ThreshCore 已有适合承载比赛方案的受控执行底座；最小样例代码已准备，但尚未在安装 AIOS/Cerebrum 的目标环境实跑。因此目前仍不能声称已满足多智能体并行、双向交互、AIOS-Agent SDK 集成或 20% 提速。下一步先跑通并检查 SDK 与 Kernel 的真实调度边界，再决定四路协作和依赖 DAG 的实现位置。
