# 五场景受控处置闭环对照表

> **产品定义**：ThreshCore = **受控处置运行时（Controlled Remediation Runtime）** + 若干运维入口。  
> 聊天 / 巡检 / 日志分析 / 知识库 / 安全信号 = 入口或证据源，**不与运行时平级**。  
> **设计过滤器**：是否直接提高「敢执行、能证明、能恢复」？不能则不进当前主线。

**状态说明**

| 标记 | 含义 |
|------|------|
| ✅ | 已具备，可作为样板依赖 |
| ⚠️ | 有实现但语义偏软 / 不统一 / 非强制 |
| ❌ | 产品强约束缺失 |

**统一目标链（样板必须对齐）**

```text
Plan → Preview → Approval → Execute → Verify → Recover → Audit
```

写执行唯一真相源：`OpsExecutionPipeline`（含门控、确认、执行、管线内 verify）。  
编排入口（`AssistantOrchestrator` / `AutonomousOpsOrchestrator`）只挂到该链，不得另起一套「差不多验证」。

---

## 一、产品义务（对内对外共同语言）

| 义务 | 含义 | 当前主线动作 |
|------|------|----------------|
| 可信处置 | 看清、提案、拦截、确认、验证、恢复、审计 | **封死五场景闭环** |
| 可复制处置 | 同 Playbook 跨时间/操作者结果可比较 | 单机先做指标与状态可比 |
| 可扩展处置 | 状态机 / 策略 / 审计稳了再 Hub/Node | V1 不做 Fleet |
| 可授权自动化 | 成功率与恢复过门槛才升自动化等级 | 默认不提高自动写等级 |

---

## 二、运行时强约束（相对现状的差距）

| 强约束 | 现状（仓库） | 诚实口径 |
|--------|--------------|----------|
| 写前声明**预期变化** | ⚠️ 契约已挂 Preview/Approval/Execute | 机读预期有；主机复采未做 |
| 写后**验证指标**对照 | ⚠️ `verifyOutcome` + 成功门控（未验证不得 success） | 以工具回执为主；`VERIFY_WEAK` 不算闭环 |
| 可逆操作**恢复入口** | ⚠️ `RecoverSpec` + 前端展示；删除走回收站 | UI 一键恢复仍弱 |
| 审计完整链 | ⚠️ 相位常量 + 巡检续办/编排已打 verify/recover 步进 | 与 MCP 管线仍双路径 |
| 组织级 Approval | ⚠️ 字段已挂；HMAC 确认仍是执行门 | 双人强制未做 |

README 原文「尽可能进行前后状态验证」视为**过时软表述**；验证是核心卖点，不是增强项。

## 三、五场景对照（样板）

### 共用能力底座

| 环节 | 主要实现 | 评定 |
|------|----------|------|
| Plan | `AgentSkillPlan`、YAML Skills、编排器计划相位 | ✅ |
| Preview | 工具 `dryRun` + `OpsExecutionPipeline.propose` | ✅ |
| Approval（令牌确认） | `confirmExecute` + HMAC / 能力令牌 | ✅ 确认有；⚠️ 组织审批弱 |
| Execute | `OpsExecutionPipeline` → MCP 分发 | ✅ |
| Verify（管线） | 写证据 + 业务预期 / `verifyOutcome` + success 门控 | ⚠️ 契约层硬了；主机复采未做 |
| Verify（效果） | `RemediationEffectEvaluator`（编排评分，配套） | ⚠️ 与管线并存 |
| Recover | `RecoverSpec` + 回收站 + 前端提示 | ⚠️ |
| Audit | 相位 + 巡检续办 verify/recover 步进 | ⚠️ 双写路径仍在 |
| 门控 | `McpInvocationSecurityGate`、`PlanEffectGate`、路径策略 | ✅ |
| 不可逆分 | `ToolEffect.irreversibility`、会话风险预算、契约不可逆文案 | ✅ |

---

### 场景 1：磁盘空间处置

| 项 | 内容 |
|----|------|
| 入口 | Agent 对话（磁盘压力）、巡检告警续办、MCP |
| 观测 | `DiskTool` / `DiskOpsTool`（只读） |
| 写工具 | 通常落到 `CleanTempTool` / `LogCleanupTool`（或 `DiskOpsTool` 写动作） |
| Plan / Preview | ✅ |
| Approval | ⚠️ HMAC 确认 |
| Execute | ✅ 须走管线 |
| Verify | ⚠️ 应强制：执行前声明 `diskUsagePct` 预期方向；执行后 `DiskTool` 复采对照；失败 → `VERIFY_FAILED` | ✅ 契约 `PATH_USAGE` + 管线/编排 `verifyOutcome`；主机复采加深仍为后续 |
| Recover | ⚠️ 依赖清理是否走 safe_delete/回收站 | ✅ `RecoverSpec.recycleBin`；句柄可回填 |
| Audit | ⚠️ 需能串起观测→提案→确认→清理→磁盘复采 | ✅ verify/recover 步进已挂；复采链路可继续 |
| **样板缺口优先级** | 预期声明 + 磁盘指标 Verify 状态机 | 主机级复采与巡检续办 trace 关联 |

---

### 场景 2：临时文件清理

| 项 | 内容 |
|----|------|
| 写工具 | `CleanTempTool` |
| Plan / Preview | ✅ `dryRun` 默认预览，真实删需 `dryRun=false` + `confirmDelete` |
| Approval | ⚠️ HMAC / 二次确认 |
| Execute | ✅ |
| Verify | ⚠️ 管线写证据有；缺「清理前后目录用量/候选数」强制对照 |
| Recover | ✅/⚠️ `safe_delete` → 回收站 list/restore；须确认真实删路径 100% 可回收或显式标不可逆 |
| Audit | ⚠️ |
| **样板缺口优先级** | 回收率保证 + Verify 业务指标 + 审计 Recover 步进 |

---

### 场景 3：日志清理

| 项 | 内容 |
|----|------|
| 写工具 | `LogCleanupTool` |
| Plan / Preview | ✅ 路径白名单 + dry-run；受保护文件跳过 |
| Approval | ⚠️ |
| Execute | ✅ |
| Verify | ⚠️ 同临时文件；另需「受保护文件未被删」断言 |
| Recover | ⚠️ 同回收站路径 |
| Audit | ⚠️ |
| **样板缺口优先级** | 与场景 2 共用删除闭环契约；保护文件校验进 Verify |

---

### 场景 4：服务重启

| 项 | 内容 |
|----|------|
| 写工具 | `ServiceRestartTool`（及网关别名） |
| Plan / Preview | ✅ `dryRun` + `confirmRestart` |
| Approval | ⚠️；白名单服务 |
| Execute | ✅ |
| Verify | ⚠️ 应强制：重启后 unit `active`/`running`（或约定健康检查）；失败明确状态 |
| Recover | ❌ 无「撤销重启」；**必须在 Preview/Approval 标注不可逆（或仅可补偿）** |
| Audit | ⚠️ |
| **样板缺口优先级** | 不可逆标注 + 服务状态 Verify；不伪造 Recover |

---

### 场景 5：巡检发现后的续办处置

| 项 | 内容 |
|----|------|
| 入口 | `AssistantOrchestrator.runPatrolContinuation`；巡检 → 提案 → 确认 |
| 观测 | `OpsPatrolService` + 本机负载/磁盘/进程等 |
| 写工具 | 按提案挂到清理/重启等白名单工具 |
| Plan / Preview | ✅ 有续办与 await confirm |
| Approval | ⚠️ `confirmPendingFromAssistant` + 令牌确认 |
| Execute | ✅/⚠️ 须保证不绕过 `OpsExecutionPipeline` |
| Verify | ⚠️ 续办路径会 `captureMetrics` / `evaluate`，仍非统一 Verify 状态 |
| Recover | ⚠️ 取决于落到的写工具 |
| Audit | ⚠️ 续办 trace 须与工具管线 trace 可关联 |
| **样板缺口优先级** | 续办状态机与管线相位对齐；禁止「编排内直接写」旁路 |

## 四、双编排约束

| 编排器 | 职责 | 约束 |
|--------|------|------|
| `AssistantOrchestrator` | 对话态：磁盘/CPU/巡检续办等 | 写操作只经管线；Verify/Recover 语义与管线一致 |
| `AutonomousOpsOrchestrator` | 偏自动巡检编排 | 同上；不得单独发明评分即等同 Verify |

封核验收时：**五场景在两条入口上的写路径都要抽检**，避免只钉死一条。

## 五、冻结扩张（已有能力降级为配套）

**保留（运行时配套）**

- 本机 CPU / 内存 / 磁盘 / 服务状态观测  
- 验证前后指标采样  
- 验证成功案例的窄 AWM  
- 失败/拦截 Reflexion  

**冻结扩张（不进当前主线）**

- 大一统安全信号平台、复杂关联引擎  
- 大规模知识库 / 通用 RAG 中台、更多数据源  
- Hub/Node Fleet、网安扫描编排  
- 完整 ITSM / 多人协同 / 开放 API 生态  
- 提高自动化写等级 / 第三方 MCP 生态  

已有模块**不删除**，但产品叙事与迭代预算不再按「平台功能」扩张。

## 六、封核工作顺序（只做闭环，不加功能面）

1. ✅ **契约**：`expectedEffect` + `verifyOutcome`（含 `VERIFY_WEAK`）+ Recover 句柄  
2. ✅ **管线门控**：真实写验证未通过 → `success=false` / `verifyBlocked`  
3. ✅ **相位**：Approval/Recover 常量 + AgentExecutionState v2  
4. ⚠️ **五场景收敛**：编排旁路 + 巡检续办已挂验证；**未**合并为唯一写入口；主机复采未做  
5. ⚠️ **最小审批字段**：已挂展示；双人强制未做  
6. ⏳ **交付底线**：并发 / 麒麟冒烟并行  

### 收敛结论（2026-08-29）

- 已做到：弱通过不再算闭环；巡检续办与管线共用验证语义；前端可见预期/验证/恢复。  
- 未做到：编排直调工具仍绕过 `OpsExecutionPipeline` 执行入口；主机指标复采；双人审批强制。  
- **暂不进入**主机复采 / 双人门控 / 多机等下一阶段，直至「成功语义」在真实演示路径上稳定。

## 七、样板完成定义（Definition of Done）

当且仅当五个场景均满足：

1. 写前有可机读预期变化；  
2. 写后有对照验证，失败为明确状态；  
3. 可逆有恢复入口，不可逆执行前明确标注；  
4. 审计可还原「提案—确认—执行—验证—（恢复）」；  
5. 不新增与闭环无关的能力面；  

方可宣称：**单机受控处置运行时核心已封死**。此后才评估可复制性指标与 Hub/Node 立项。
