# 数据库版本迁移与日志任务恢复

本页涵盖数据库版本、日志任务恢复、模块结构、Skill 发布治理与独立日志 AI 诊断任务。AgentTeams 已接入独立角色、人工批准与接管，见 [AgentTeams 运行与接管](AgentTeams运行与接管.md)；真实模型闭环实测和外部写操作的自动跨进程恢复仍待补齐。

## 数据库升级

数据库迁移使用 Spring Boot BOM 管理的 Flyway，默认启动校验、禁止 clean。迁移历史在 `flyway_schema_history`，不得修改已经发布的迁移文件或对其自动 repair。

- V1 创建结构，不导入示例账户、默认口令、演示规则，也不删除原有数据。
- V2 补齐旧日志任务的 `user_id`，并创建 `log_task_runtime`，保存输入摘要、执行标识、实例、阶段、心跳、租约和报告状态。
- V3 接管工作流、失败教训、用户偏好/API Key、告警规则、人工反馈、访问审计、审批、告警生命周期、运维审计和巡检历史的结构。原模块启动时建表/加列的代码已移除，缓存加载保留。
- V3 根据数据库元数据补齐列、索引和外键；字符串只允许扩宽。MySQL 扩宽保留原默认值、可空性、字符集、排序规则及注释。不兼容类型、错误索引或重复邮箱导致的唯一约束失败会阻止升级，不能靠吞异常继续启动。
- V4 保存 Skill 不可变制品、历史版本指纹、当前发布指针、发布/回退记录和运行版本绑定。
- V5 保存日志 AI 诊断的独立尝试、请求幂等标识、实例、总截止时间、状态和错误码；不将旧诊断文本追认为成功结果。
- V6 保存团队运行、角色交接、人工门控、写入意图、工具回执与需明确核对后释放的团队资源锁。
- V7 新增按用户和请求键唯一的日志上传幂等记录，保存内容 SHA-256 与任务 ID；相同请求重试复用原任务，内容变化返回冲突，过期孤立预留允许重新接管。
- 旧 `schema.sql` 删除告警规则表的语句已移除；正式升级使用版本迁移，不重复导入旧演示脚本。

新空库直接执行迁移。已有业务表且没有迁移历史的库默认拒绝自动接管；先完成备份并核对数据库实例、名称、权限和原有表结构，再在首次升级启动时显式设置：

```powershell
$env:THRESH_DB_ADOPT_LEGACY = 'true'
```

确认全部迁移成功和旧数据保留后，移除此临时设置，恢复默认 `false`。接管的 baseline 为 0，因此 V1 至 V7 都会执行。不能把接管开关长期作为跳过校验的开关。

MySQL/MariaDB 的 DDL 可能自动提交。迁移失败须检查已执行操作和备份，制定修复迁移或恢复备份，不能承诺事务会撤销所有 DDL。新库的管理员账号须通过明确的账号初始化流程创建，迁移不植入通用默认账号。

参考：[Spring Boot 数据库初始化](https://docs.spring.io/spring-boot/how-to/data-initialization.html)、[Flyway Java 迁移及校验](https://documentation.red-gate.com/flyway/flyway-concepts/migrations/java-based-migrations)。

## 日志任务运行与恢复

上传在进入异步队列前保存独立输入副本及 SHA-256。实际分析读取该副本，临时上传文件随后清理。每次领取任务生成新的执行标识，只有当前且未过期的执行才能更新进度或提交分析结果；分片线程也携带同一标识。

默认配置：

```yaml
log:
  analysis:
    input-dir: ./data/log-inputs
    lease-seconds: 90
    heartbeat-ms: 10000
    input-retention-hours: 24
```

心跳必须短于租约的一半，保留时间必须为正数。生产应将输入目录设置在受访问控制、容量受监控的持久磁盘上。该目录已排除出 Git，不应上传比赛或研究材料。

- 正常关闭时，未完成任务进入 `RECOVERY_REQUIRED`。
- 进程异常退出后，超过租约且未续约的任务由启动/定时对账标记为待恢复；不会抢占其他实例的有效租约。
- 用户打开任务后，可选择“从保存的日志重新分析”。恢复会核对输入路径和摘要；缺失、内容变化或路径重定向时拒绝恢复。
- 旧任务没有保留输入时显示需要重新上传，不将它们伪装成可恢复任务。
- 取消或删除后的任务不能恢复；旧执行实例的结果不能覆盖新的执行。
- 当前恢复的是只读日志分析的重新计算，不自动重放外部写操作，也不是从任意一行继续计算。
- 共用数据库的实例需访问同一保留输入存储才能接续分析；本批不提供跨机器输入传输或远程执行。

完成、失败、取消任务的输入默认保留 24 小时后清理；待恢复任务的输入保留到用户处置。删除任务立即尝试清理文件，清理失败会保留待清理记录，由维护任务重试。需为长期未处理任务制定容量和人工处置策略。

## 文件实时采集边界

`FileLogCollector` 按 UTF-8 字节增量解码。尚无换行的尾部暂存，等后续换行后发布，跨次写入的多字节字符不会被提前解码。兼容 LF、CRLF 和独立 CR，文件首部 UTF-8 BOM 会移除。此规则针对实时采集，不改变上传文件的批量分析接口。

单文件每轮最多读取 1MiB、发布 2000 行；单采集器缓冲受配置行数和固定 8MiB UTF-8 内容字节数共同限制。满后保留当前行和游标，排水后继续读取；目录监听空闲时定时补采，不依赖文件再次修改。8MiB 是正文载荷上限，不是 JVM 总内存上限；待完成行按文件暂存，每行最多 64KiB。

超过 64KiB 的物理行整行跳过至下一换行；非法 UTF-8 行跳过并计数，避免将乱码作为正常证据。`GET /api/collector/status` 的 `collectorDiagnostics` 可查看文件采集器的 `encoding`、`bufferedLines`、`bufferedBytes`、`backpressureEvents`、`oversizedLines`、`invalidUtf8Lines` 及各项固定上限。查询不会排空采集缓冲，计数为当前进程累计值，重启会重置。

轮转时优先检测文件标识，并用游标前 64 字节的 SHA-256 辅助识别 Windows 缺少 `fileKey` 时的文件替换、截断及重新增长。此辅助检测不能证明所有轮转均无损：若替换文件的检查窗口内容相同，或旧文件未读内容已被删除，仍可能无法识别或补回。多行异常栈当前保留物理行次序，跨行事件聚合、其他编码和目标 Linux 文件系统轮转仍需后续验证。

### 实时文件检查点与交付确认

默认 `log.collector.file.checkpoint-directory=./data/collector-checkpoints`（环境变量 `LOG_COLLECTOR_CHECKPOINT_DIR`）。目录属于私有运行数据，需受访问控制、持久保存和容量监控；文件含源路径、字节位置、文件标识及内容窗口的哈希，不保存日志正文。显式空值关闭持久化。按规范化采集根路径分隔状态，不依赖自动生成的采集器名称；相同根路径和检查点目录由文件锁限制为一个持有者。

`start-at-eof` 仅决定没有检查点的新文件的初始位置。已有检查点优先恢复，不因启动配置仍为 `true` 而跳到新 EOF。读取游标与已确认游标分离；仅保存完整物理行边界及 CRLF 状态，半行和未交付缓冲在重启时从源文件重读。

当前调度器等待整批 Kafka 发送收到代理回执，随后才推进该批快照对应的检查点。发送失败、异步发送尚未结束或检查点写入失败时保留原批次；重试保留该批事件 ID，暂停从采集器排取新批次，使文件缓冲继续受原背压限制。启用 Kafka 时启动校验要求显式配置 `acks=all` 或 `-1`；缺失、`0` 或 `1` 均拒绝启动，默认部署配置保持 `all`。检查点采用先写临时文件、强制刷新文件、再原子替换；不支持原子替换时明确失败，不退回普通覆盖。此实现未证明断电情况下目录元数据的持久性。

未启用 Kafka 时，本地 WebSocket/fan-out 内存队列不具有持久确认资格，因此只建立初始检查点，不随排水前进；重启会回放初始位置之后的日志，可能重复。该模式仍需后续增加本地持久消费账本，不能作为可靠存储或端到端无损分析链路。源文件保留时间必须覆盖未确认区间；旧文件被删除或覆盖后，检查点本身无法恢复正文。

交付语义为允许重复的重新交付：代理已接收但检查点未写成时可再次发送；进程重启后新生成事件 ID 也可能变化，当前不提供跨进程去重保证。Kafka 回执不代表下游完成分析、告警或数据库入库。检查点损坏和占用冲突不会静默清零或跳到 EOF；须核对源文件与交付记录后人工处理，不能直接删除检查点当作恢复操作。

`GET /api/collector/status` 增加 `checkpointReceiver`、`pendingDeliveryLines`、`dispatchFailures`；文件采集诊断增加 `checkpointEnabled`、`checkpointError` 和 `checkpointBoundary`。实时采集检查点与上传分析的保留输入恢复是两套机制。

自动根路径通过真实规范路径去重，避免 `logs` 与 `./logs` 启动重复采集器。应用容器关闭会停止全部采集器并释放检查点持有锁；一个采集器关闭失败也会继续关闭其他采集器，最后报告汇总异常。Windows 在子进程退出后释放原生句柄可能有短暂延迟；重启遇到占用应确认旧进程已结束后再重试，不能跳过锁。

## 报告一致性

报告生成和删除使用同一数据库任务行锁，适用于共享数据库、共享报告存储的多个应用实例。导出先写临时目录，再以原子文件移动发布 CSV/HTML；不支持原子移动时明确失败，不降级为可见的半文件复制。

报告状态与 AI 诊断状态分别记录，模型失败不会修改已完成的确定性分析和报告状态。

任务删除提交之后才清理文件，回滚不会提前删除报告。删除记录保留在运行表中；排队的旧导出在取得锁后再次核对业务任务，已删除时不会生成文件。清理元数据由后续维护事务对账，避免提交回调占满连接池。

## 独立日志 AI 诊断

日志页面使用 `POST /log/diagnosis/{taskId}` 提交 `{ "requestId": "客户端生成的唯一标识" }`，用同路径 GET 查询状态。只有已完成且属于当前用户（或管理员可访问）的分析任务可以诊断。普通账户不能读取、启动或取消他人的诊断。

- 状态为 `NOT_REQUESTED`、`QUEUED`、`RUNNING`、`SUCCEEDED`、`FAILED`、`TIMED_OUT`、`CANCELLED`、`INTERRUPTED`；旧文本未有成功证明时为 `UNTRACKED`，仍保留原数据，但不会作为新成功结果返回。
- 同一 requestId 重发不增加尝试；同一任务存在活动诊断时复用它。失败后由用户明确使用新 requestId 重试，不自动重放模型请求或拼接重试前的部分回复。
- 每个任务默认最多 3 次尝试，总时限 120 秒，包含排队、取样与模型响应。配置为 `log.diagnosis.max-attempts`（1–10）、`log.diagnosis.timeout-seconds`（1–300）。这是调用次数与总时间限制，尚不是供应商 token 或费用记账。
- 独立执行池为 2 个线程、20 个排队任务；队列拒绝明确记录 `QUEUE_REJECTED`。输出限制为 60 KiB UTF-8 字节，防止中文结果超出 MySQL TEXT 容量。
- `POST /log/diagnosis/{taskId}/cancel` 提交当前 `runId`，取消不删除解析结果。旧 runId 无权取消新尝试；取消、删除、超时、旧尝试的迟到输出不能覆盖结果。
- 每次尝试的成功文本、任务当前诊断、诊断状态在同一事务中提交。重复旧 requestId 返回其原尝试结果，不混入新尝试的正文。模型异常、空回复、超限、超时分别保留安全错误码，不把异常说明当成诊断正文保存；删除任务同时清除各次尝试的正文，保留无正文的状态记录。
- 诊断依据有限的异常样本和前 100 条明细中的正常对照；提示词限定样本证据，不声称已阅读所有日志或证明整个系统健康。完整业务基线与取样充分性评测仍待补齐。
- 正常关闭标记活动诊断中断；异常退出的任务超过持久截止时间后标记超时，用户可明确重试。页面断线不自动取消后台任务，重新打开可读取其最终状态。删除任务会在同一事务中取消活动诊断。

旧同步 `/log/diagnose/{taskId}` 和可选旧任务 SSE 接口复用这一任务服务；日志页面不依赖默认关闭的 legacy SSE。单行快速诊断及自动告警的模型调用尚未全部纳入此任务账本，统一模型治理随下一批继续推进。此处通过测试替身验证失败、取消和接口行为，不构成真实外部模型效果证明。

## 回归入口

文件实时采集新增 10 项固定样本：UTF-8 多字节与半行、CRLF 与 BOM、行数和字节背压、超长行、非法编码、截断、替换文件、同文件重写及目录空闲补采；Windows 本机测试通过。这些测试不证明实时游标跨进程恢复或所有目标文件系统均无损轮转。

随后新增 23 项回归，覆盖持久检查点、异步交付确认、失败批次重试、采集根去重和容器关闭。检查点用例包含独立 JVM：确认第一批后，将第二批保留在内存，强制终止子进程，再使用同一检查点重新采集，已确认行不重放、未确认行重新读取。该用例验证 Windows 本机进程异常退出，不代表整机断电、源文件已删除或所有文件系统轮转。Kafka 回执、异步失败和配置校验使用测试替身，尚未连接真实代理验证；未将代理接收等同于下游分析入库完成。API/数据库集成测试关闭真实主机采集，由上述专门用例单独验证采集行为。


2026-10-29 本轮验证：完整 `mvn -o -q -Dmaven.repo.local=target/maven-cache verify` 为 1235 项、0 失败、0 错误、1 跳过；指令覆盖率 80.8804%，通过原 80% 门禁。独立原生 MySQL 8.0.45 验证迁移、中文结果持久化和取消后旧结果隔离；诊断 HTTP、超时及故障用例使用模型替身。没有升级业务数据库，没有将这些结果作为真实外部模型或麒麟/LoongArch 实测证明。

常规完整验证：`mvn verify`；前端：在 `frontend/` 执行 `npm test`、`npm run build`。

数据库与任务定向验证：

```powershell
mvn '-Dtest=DatabaseMigrationTest,DurableLogTaskStoreTest,DurableLogFlowIntegrationTest' test
```

原生 MySQL 兼容性测试仅对独立、可销毁的本机测试实例显式运行：

```powershell
mvn '-Dtest=MySqlMigrationIT' '-Dthresh.mysql-test.server=jdbc:mysql://127.0.0.1:33087/' test
```

测试服务器的数据目录必须命名为 `threshcore-mysql-canary-` 加 32 位小写十六进制随机串，测试会检查 `@@datadir`，避免误用本机日常数据库。测试创建随机命名的 `threshcore_canary_` 数据库，并在结束时删除自己创建的库。其余凭据通过测试专用系统属性传入，不写入项目配置或提交记录。

常规 `verify` 不运行该 `IT` 类；独立实例就绪时可使用 `mvn -Pmysql-compat '-Dthresh.mysql-test.server=jdbc:mysql://127.0.0.1:33087/' verify`，在保留常规完整测试的同时追加原生数据库兼容性测试和覆盖率门禁。需记录实际数据库版本与结果。

## Skill 发布、回退与运行绑定

首次空发布库会校验部署包内的 14 个 Skill，并通过固定契约用例后建立初始发布。已有发布记录时，启动读取数据库中的当前制品；不会因部署 YAML 变化而隐式覆盖已批准版本。因此回退后重新启动仍读取回退版本。

管理员在“运维工具与诊断 → YAML SOP”中填写原因，先预览部署版本，查看版本差异和评测结果，再发布已预览版本。发布同时绑定预览时的活动目录指纹和候选指纹；当前版本、部署内容变化或评测失败时拒绝操作。普通账户只能查看当前目录，管理接口还会在服务端核对管理员身份。

管理接口：

- `POST /api/ops/skills/releases/preview`：预览部署包中的候选目录，不激活。
- `POST /api/ops/skills/releases/publish`：提交 `expectedFingerprint`、`candidateFingerprint` 和 `reason`。
- `POST /api/ops/skills/releases/rollback`：提交 `expectedFingerprint`、可选 `targetFingerprint` 和 `reason`。省略目标时选择上一次发布。
- `GET /api/ops/skills/releases/history`：管理员读取启用与回退记录。

同一 Skill 的相同版本号不能改换内容，此约束在回退之后仍保留。隐式版本下降、过期批准和损坏制品均被拒绝。已发布迁移文件不可修改；后续数据库变更继续增加新迁移版本。

当前门禁为 `contract-eval/v1`：14 个 Skill 的工具/剧本契约、独立信号正常/缺失/重复/为空的边界，以及显式预览优先规则，共 73 项检查。它不调用真实模型或主机工具，不是业务效果或故障恢复成绩；真实模型、平台能力、输入输出细分契约与业务数据评测仍需后续补齐。

`AssistantOrchestrator` 与 `AutonomousOpsOrchestrator` 在开始运行时将 trace 绑定到不可变发布制品，运行中热发布不改变该运行的 Skill；审计步骤记录目录指纹。其余模型直连入口将随统一运行时继续整合，当前不宣称所有路径均已绑定。
