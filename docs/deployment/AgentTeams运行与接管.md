# AgentTeams 运行与人工接管

## 当前实现

工作台新增“协作处置任务”。一个运行包含三个独立的模型角色调用：诊断角色引用采集证据；计划角色提交工具步骤、预期效果、只读验证探针和停止条件；验证角色读取执行后的新证据。系统负责调度、预算、批准和工具执行，模型侧工具自动执行明确关闭。

这不是多进程或多主机系统。角色输出为结构化交接摘要，不采集或展示模型私有思维过程。原对话编排入口保留，本页提供新的协作运行入口；不能据此宣称所有旧入口已迁入同一团队运行时。

## 持久状态与恢复边界

Flyway V6 新增 `ops_team_run`、`ops_team_event`、`ops_team_resource_lock`。运行保存操作者、请求幂等标识、固定 Skill 制品指纹、观测参数、阶段、修订号、执行标识、模型调用计数、活动时间余额和计划指纹。角色输入、输出、模型返回的名称、耗时、人工批准、接管原因、写入意图和工具回执进入独立事件时间线。

正常流程：

`QUEUED → COLLECTING → DIAGNOSING → PLANNING → PREVIEWING → WAITING_APPROVAL → EXECUTING → VERIFYING → COMPLETED`

- 同一账户的同一 requestId 复用原运行；内容不同则拒绝。不同实例不能领取同一执行标识。
- 活动时间默认共 180 秒，配置 `agent.teams.active-budget-ms`，允许 1–600 秒；等待人工批准不消耗活动时间。模型角色调用默认最多 6 次，配置 `agent.teams.max-model-calls`，允许 3–12 次。这是角色调用计数，未实现供应商 token、费用或底层 SDK 重试次数的独立账本。
- 每阶段最多 3 个采集探针、3 个计划步骤、3 个验证探针。证据正文有大小限制并显式标注截断；不能将截断样本描述为全量分析。
- 开始时固定 Skill 发布制品。模型和人工计划均受其工具集合限制；验证探针只读。诊断引用必须存在，并满足 Skill 对独立证据来源的最低数量要求。
- 每个执行窗口有独立标识。过期执行无法发布新的状态或完成结果。进程异常退出后，超过持久截止时间进入 `NEEDS_HUMAN`，不会自动重放写入。
- 工作线程失败会追加 `WORKER_FAILURE` 时间线事件，记录失败阶段、稳定错误码、异常类型和脱敏截断后的摘要；不记录堆栈或原始输入。
- 批准凭证仅保存在当前进程内，绑定运行、计划指纹和修订号。服务重启或凭证过期后，需要重新预览和批准，数据库中的旧批准事件不能直接恢复执行权限。
- 最终完成同时要求写工具管线的强验证通过、执行后只读采样成功、独立验证角色引用新证据并返回 `VERIFIED`。模型的成功文本不能覆盖管线的验证失败。

停止条件文字供操作者和模型核对；系统独立强制证据、契约、预算、权限、批准和效果验证规则。本版本未实现任意自然语言停止条件的自动解释执行。

## 人工批准与接管

1. 选择 Skill，填写问题与证据采集参数。采集对可写工具仅执行预览。
2. 核对诊断、计划、候选对象、预期效果和恢复说明。
3. 输入“确认执行”，提交当前计划指纹和修订号。所有真实写入调用现有 PEP 的 `executeConfirmed`，不由模型直接分发。
4. 需要修改时，在“人工接管”中载入计划、填写原因并提交。系统重新采集证据、生成预览；旧版本批准失效。
5. 如果已经记录写入意图，停止、超时或失败会显示需要接管。必须核对现有回执和外部实际状态，明确勾选已核对外部影响后，才允许释放该团队运行保留的资源锁并重新预览。不能把停止任务视为撤销已发生的操作。

诊断缺证据时，可在人工接管中载入并修改采集配置，填写原因后重新采集、诊断和规划。系统继续使用原运行固定的 Skill，校验工具和参数，并保留人工操作事件；旧计划、诊断和批准失效。若已有写入意图，仍须先核对外部状态且原执行线程已退出。重试需要至少剩余 3 次角色调用预算；预算不足时应新建任务，而不是绕过上限。

取消后的迟到工具回执只能追加为证据，不覆盖接管状态。即使 Future 已取消，只要原写入线程还在运行，系统也拒绝重新接管执行。

团队运行之间对文件系统写入采用保守的本机整体互斥，避免目录祖先/子路径冲突；服务、进程、容器等按效果目标建立锁。锁不因超时自动释放。当前这些锁由 AgentTeams 入口使用，其他旧入口的全局资源协调仍待统一，不能宣称覆盖项目所有写入入口。

持久化 Runbook 审批入口也已接入同一 `OpsExecutionPipeline`：批准时生成对象预览和一次性凭证，执行时消费该凭证并复核对象、验证效果。凭证绑定批准操作者；其他操作者不能消费。重启或过期后，未执行工单需要重新调用批准接口。数据库批准记录不自动恢复执行权；缺少统一管线时直接拒绝批准和执行。

执行前使用数据库条件更新将当前批准领取为 `EXECUTING`，同时核对批准关联的 trace。新批准使旧实例凭证失效；重复请求不得再次调用工具。若调用后回执或落库失败，数据库保留 `EXECUTING`、操作者、执行时间和批准 trace，禁止自动重放。此状态需要人工检查主机与管线审计；支持下述在线人工核对结案。自动外部状态对账仍待实现，AgentTeams 的接管接口保持独立。

### Runbook 人工核对结案

管理员可调用 `POST /api/runbook/{id}/reconcile`，提交当前列表中的 `traceId` 为 `expectedTraceId`，填写 `outcome`、`evidence`，明确设置 `externalEffectsReviewed: true` 并输入 `confirmCode: "核对结案"`。仅 `EXECUTING` 可结案，状态或 trace 变化返回业务码 409；缺失证据、确认或非法结论返回 400，非管理员返回 403。

`outcome` 可选 `EFFECT_CONFIRMED`（人工确认影响）、`RECOVERED`（人工确认已恢复）、`NO_EFFECT`（人工未发现影响）、`UNKNOWN`（影响仍不确定）。这些均为人工声明，证据与结案状态在同一次数据库更新中持久化。记录保存核对人、核对时间、原执行 trace、脱敏后的证据及 `source: HUMAN_REVIEW`、`automaticVerification: false`，原结果保留在 `previousResult`。

结案后状态为 `MANUALLY_CLOSED`，原工单不可再次批准或执行。此操作只关闭行政记录，不发送停止、恢复或重试命令，也不证明其他进程的工作线程已退出。跨实例结案期间若原线程仍返回，工具回执追加到 `lateReceipt`，保留人工结论、结案状态及原始 trace；需结合迟到回执继续核对外部状态。该功能为 API 交付面，当前无专用前端表单。

## 接口

所有接口要求登录，并在服务端校验运行归属；管理员沿用项目现有管理权限。API Key 的只读端点白名单保持原规则，不开放团队写入操作。

| 方法 | 路径 | 请求或用途 |
|---|---|---|
| GET | `/api/agent-teams` | 当前账户最近 50 个运行；管理员可查看管理范围 |
| GET | `/api/agent-teams/skills` | 当前可选择的 Skill |
| POST | `/api/agent-teams` | `requestId`、`goal`、`skillId`、`observations` |
| GET | `/api/agent-teams/{id}` | 状态、修订号、计划、预览和事件；不返回批准票据 |
| POST | `/api/agent-teams/{id}/approve` | `revision`、`planHash`、`confirmCode` |
| POST | `/api/agent-teams/{id}/plan` | `revision`、`plan`、`reason`、`externalEffectsReviewed` |
| POST | `/api/agent-teams/{id}/evidence` | `revision`、`observations`、`reason`、`externalEffectsReviewed`；仅人工接管状态可用 |
| POST | `/api/agent-teams/{id}/cancel` | 停止后续步骤，保留已有影响的核对线索 |

状态变动、过期批准、版本不符返回 409；非法契约返回 400；无权访问与不存在均返回 404。页面活动阶段每 1.5 秒轮询，等待批准或人工接管时每 5 秒轮询；临时断线逐步退避重试，登录、权限或任务不存在错误停止重试。修订号或计划指纹变化时清空确认码和外部影响核对勾选；已编辑的旧计划及采集配置必须重新载入，服务端也拒绝过期修订号。该机制使用轮询，尚不是 SSE 断线续传。

## 2026-10-29 验证记录与限制

### 执行前持久审计

HTTP 执行入口 `/api/mcp/execute`、`/api/mcp/confirmExecute` 已移除历史直调和重复确认实现，统一委托 `OpsExecutionPipeline`。预览请求只进入预览，不能由 HTTP 层将其改为实写。确认时忽略客户端补送的工具与参数，使用服务端保存的批准快照。旧的 `ops.pep.enabled=false`（或环境变量 `OPS_PEP_ENABLED=false`）会在启动时被明确拒绝；部署升级需删除该关闭配置或设为 `true`。此变更不新增全局资源冲突协调，其他内部调用路径仍需分别核对。

需要演练而不执行真实写入时，应使用现有全局演练模式 `ops.dry-run.global=true`，同时保持 PEP 启用。关闭安全门控不再作为演练或兼容运行方式。部署升级前请检查环境文件、启动参数和本地覆盖配置中的旧关闭项。

`OpsExecutionPipeline` 的确认执行和直接放行执行在调用真实写工具前，必须保存 `write_intent` 审计。记录包含 trace、操作者、效果指纹、策略版本、会话关联及经过基础凭据脱敏的参数，`execution_ok=0`，明确表示执行意图，不能据此认定写入或验证已完成。

该记录通过独立 JDBC 事务提交，外层业务事务回滚不会撤销它。审计表不可用、插入失败、事务无法提交或身份缺失时，管线返回 `AUDIT_UNAVAILABLE`、`phase=audit`、`writeStarted=false`，不调用写工具。已核销的确认凭证仍然失效，恢复审计后需重新预览确认。执行前只读观测或预览可能已经发生；该错误不表示请求中未做任何只读工作。

执行后结果仍通过原审计适配层记录。若写入后审计发生故障，执行意图可以用于定位，但外部效果仍需核对，不能自动重放。独立事务会额外使用一个数据库连接，需为业务事务及并发写入预留连接池容量。此约束覆盖统一管线入口，不等于其他绕过管线的历史工具调用均已治理。

新增定向回归验证独立事务记录在外层回滚后保留、真实 H2 审计存储故障、身份缺失、后台操作者关联，以及确认/直接写路径在审计失败时阻止实写。模型实跑仍待授权，未因本次审计改造启用外部模型验收。
